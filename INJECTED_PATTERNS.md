# Injected Fraud Patterns: What the GNN Must Learn

Generated by [`00_inject_fraud_patterns.py`](00_inject_fraud_patterns.py) (seed 42, deterministic).
Input: `Dataset/PS_20174392719_1491204439457_log.csv` (original PaySim, never modified).
Output: `Dataset/PS_augmented.csv` (PaySim + 15,636 injected rows) and `Dataset/injected_manifest.csv` (one line per injected row: pattern, instance, role, label, holdout).
Checked by [`09_evaluate_patterns.py`](09_evaluate_patterns.py) after retraining.

## 1. Why the injection was needed

On PaySim's TRANSFER + CASH_OUT rows:

| | Fraud | Legit |
|---|---|---|
| Receiver shared with other transactions | 62.2% | **95.5%** |
| Median transactions per receiver | 3 | **9** |
| Sender has other transactions | 0.2% | 0.1% |

Legit transactions are much better connected than fraud. The trained GNN therefore learned the shortcut **"more neighbours = more normal"**: connecting a transaction to *known fraud* lowered its score. Measured on the current checkpoint:
- a drain-to-mule transfer scores 56.8% alone, but 29.4% when linked to 3 drain-pattern transactions;
- on the injected patterns, adding neighbours lowers fraud scores by 0.15–0.29 on average.

PaySim also has almost no repeat senders, so sender-side fraud (structuring, takeover bursts) doesn't exist in it at all.

## 2. What was injected

Every fraud pattern puts **fraud next to fraud**, so neighbours should push the score **up**. Two kinds of legitimate twin keep the model honest:
- **Group twins:** legit groups with the same overall shape (payroll vs smurfing, busy agent vs collusive agent…), so "being in a group" isn't fraud.
- **Isolated twins:** an **exact copy of every fraud row** of the five graph-only patterns. Same step, type, amount and balances, but sent between unrelated accounts, with no neighbours. Row by row, fraud and twin are identical, so a tabular model such as XGBoost **cannot** tell them apart. Only the graph can.

All rows of one instance fall inside the graph builder's 24-step window, so they really are connected in the graph. Instances never connect to each other or to original PaySim rows.

### Fraud patterns (label 1)

| # | Pattern | What happens (example) | Linked through | Instances | Fraud rows |
|---|---|---|---|---|---|
| F1 | **MULE_HUB**: fan-in | 8–15 victims are each (mostly fully) drained into **one fresh mule** within 6 h; the mule then cashes everything out at an agent. | same receiver | 70 | 886 |
| F2 | **STRUCTURING**: splitting to dodge the BB limit | One sender makes **3–6 transfers of BDT 40,000–49,999 within 2 h** and keeps a healthy balance. *E.g. 48,200 + 49,100 + 47,500 + 46,900.* | same sender | 175 | 804 |
| F3 | **SMURF_FANOUT**: placement/layering | One source spreads 60–95% of its balance over **8–20 brand-new accounts** within 3 h. Each transfer is a modest share. | same sender | 70 | 983 |
| F4 | **AGENT_COLLUSION**: collusive cash-out | 10–25 near-empty, freshly funded accounts each **cash out (almost) everything at the same agent** within 6 h. | same receiver | 45 | 782 |
| F5 | **ACCOUNT_TAKEOVER**: velocity burst | An established account makes 2–4 small normal payments (348 legit "owner history" rows), then within ~1 h sends **80–100% of what's left to 3–5 brand-new accounts**. | same sender | 110 | 443 |
| F6 | **MULE_NETWORK**: coordinated ring | 5–9 victims each send 15–30% of their balance to 2–3 mules from a **shared set of 3–5 mules**, within 4 h. No victim is drained; only the dense victim↔mule structure (2 hops) gives it away. | same sender + same receiver | 55 | 945 |

The group twins are sized to roughly match the fraud groups row for row. With half as many, the model learned "connected injected group = fraud" and flagged 83–100% of them.

The three small-account groups were added after the first full retrain. In the first version, every legit group paid an established, well-funded account, so "a small or empty account receiving several transfers" only ever appeared as fraud, and the model flagged a customer paying the same relative or corner shop twice about 75% of the time.

MULE_HUB has no isolated twin on purpose. Its rows are full drains, PaySim's classic fraud signature, which should stay detectable row by row.

**Totals:** 15,636 injected rows: 4,843 fraud and 10,793 legit.
- TRANSFER + CASH_OUT rows: 2,770,409 → 2,786,045.
- Fraud rows: 8,213 → 13,056 (0.30% → 0.47%).
- Original PaySim fraud is still the majority of the fraud class (63%).
- 20% of instances (3,225 rows, 1,006 of them fraud) are **holdout**: kept out of training and validation, used only for the checks below.

### Graph structure check (real `03_graph_builder.py` edge rule)

| Pattern | Has a neighbour | Fraud share of neighbours |
|---|---|---|
| All six fraud patterns | 96–100% (MULE_HUB: some single mule cash-outs have none) | 100% (ACCOUNT_TAKEOVER mixes in the owner's legit history) |
| Group twins | 100% | 0% |
| Isolated twins | 0% | n/a |

## 3. How to tell whether the GNN learned it

`09_evaluate_patterns.py` runs these on the holdout instances and prints PASS/FAIL. It scores with:
- the retrained model;
- the previous model, kept automatically as `models/FraudGNN_main_v1_paysim_only.pt`;
- an XGBoost trained on the same split.

| Check | Pass if | What it proves |
|---|---|---|
| **A. Recall per fraud pattern** (threshold 0.40 = REVIEW, live mode) | ≥ 80% for each of F1–F6 | The pattern was learned on instances it never saw |
| **B. False alarms per twin** | ≤ 10% scored REVIEW or above, for every twin | It didn't learn a new shortcut ("groups = fraud" or "this row shape = fraud"). The ACCOUNT_TAKEOVER owner's own earlier payments are not a twin (they sit inside the fraud group), so they're reported separately as "guilt by association". |
| **C. Neighbour effect** (score each fraud row alone vs with its neighbours) | Fraud scores go **up** with neighbours | Fixes the old behaviour (they went down by 0.15–0.29) |
| **D. Graph vs tabular:** separation = fraud flagged − isolated twin flagged | GNN separation exceeds XGBoost's by ≥ 0.30 on all five graph-only patterns | The decision comes from the graph. XGBoost scores about 0 here by construction, because the rows are identical. |
| **E. Original PaySim fraud** (non-injected test rows) | Live-mode AUC within 0.02 of the previous model | The injection didn't damage what the model already knew |
| **F. Live demo** | Scoring a pattern through the API gives REVIEW/BLOCK, and its twin ALLOW | Works end to end through Redis neighbours |

Before retraining, the previous model already scores **negative** separation on D (−0.44 to −0.77): it flags the isolated twin *more* than the connected fraud. That is the "before" number for the report.

Dry run on a 300k-row PaySim sample (CPU, same scripts and settings; the full Colab run will differ in the exact numbers):

| Check | Result |
|---|---|
| A | ✅ 97–100% for every fraud pattern (previous model: 0–25%) |
| B | ✅ isolated twins, busy agent, shared payees 0%, bill payments 10%; ⚠️ **payroll 27%** |
| C | ✅ neighbours raise every fraud pattern's score (previous model: lowered them) |
| D | ✅ GNN separation 0.97–1.00; XGBoost 0.00; previous model −0.77 to 0.00 |
| E | ✅ original PaySim AUC 0.869 → 0.865 |

Payroll is the honest weak spot: one employer paying 15 people at once has exactly the shape of smurfing; only the receivers' existing balances tell them apart.

Expected difficulty:
- **Easiest:** F1, F4 and F6. Many neighbours, all of them fraud.
- **Medium:** F2 and F3.
- **Hardest:** F5 (ACCOUNT_TAKEOVER). The owner's legit history shares the neighbourhood, so the model must separate burst from history by each row's own size and timing.

## 4. Pipeline changes (already made in the scripts)

| Script | Change |
|---|---|
| `00_inject_fraud_patterns.py` | New; produces the augmented CSV + manifest (`--src`, `--out-dir` for Colab) |
| `01_load_paysim.py` | Reads `PS_augmented.csv`; tags each injected row with `pattern` and `holdout` (verified by account id) |
| `03_graph_builder.py` | Stores `data.holdout` in the graph |
| `01_load_paysim.py` (scaling) | Amount and balances get **log1p** before `StandardScaler` (PaySim amounts have a std of ~BDT 887,000, so plain scaling squeezed 15,000 and 80,000 to almost the same number). Previous scaler/encoder kept as `*_v1_paysim_only.pkl`; transform recorded in `preprocess.json`. |
| `train_main_gnn.py` | Holdout rows go to the test split only. Training **alternates full / live mode** every epoch. Injected legit look-alikes are **hard negatives** at half the fraud weight. Best checkpoint = **validation PR-AUC** (mean of both modes) after a 30-epoch warm-up, patience 20, up to 300 epochs. Previous model backed up automatically. |
| `09_evaluate_patterns.py` | New; checks A–E |

The model architecture is unchanged. The checkpoint records `money_transform: "log1p"`, and `backend/ml_service.py` applies it automatically, so older checkpoints keep working. Copy the new `scaler.pkl` and `type_encoder.pkl` to `backend/model/` together with the model; they belong together.

## 5. Known limits

- **No money-flow edge.** The graph links transactions only by same sender or same receiver, so a mule's cash-out isn't linked to the money that flowed in. Layering chains (A→B→C→D) and round-trip cycles need a flow edge in both the graph builder and the backend's Redis lookup, so they are not injected.
- **Synthetic data.** Like PaySim itself, the patterns are simulated. They come from documented MFS fraud typologies, but the amounts and timings are designed, not observed.
- **`isFlaggedFraud`** is 0 on all injected rows; no model uses it as a feature.
